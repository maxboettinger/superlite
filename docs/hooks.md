# Hooks

`hooks/hooks.json` registers these. The run hooks are active only while a run marker exists (`.superlite/stable.json`, `prime.md` or `pool.json`, written by the first lint). They fail open on bad input.

**Which `.superlite`.** Each session has its own (`hooks/superlite-state.sh`, the same order as `scripts/state.py`): `$SUPERLITE_STATE_DIR`; else the session's binding `~/.superlite/sessions/<session_id>`, written by `sl orchestrator set|approve|bind` and `lint --stable`; else `<CLAUDE_PROJECT_DIR or cwd>/.superlite`, unless its `session` file names another live session (one whose binding points at it). A binding counts only while no other session took the folder over: `sl orchestrator bind --force`, or without `--force` a session launched in the folder's own project (line 3 of a binding records the launch directory) when the owner was launched elsewhere, as a build session launched in a worktree takes over the planning session's folder; an owner launched in the same directory still wins. `session-start` exports the hook's id as `SUPERLITE_SESSION_ID` (through `CLAUDE_ENV_FILE`), so `sl` binds under the id the hooks read; on `/clear` it hands the one binding of the same Claude process (`CLAUDE_PID`, line 2 of the binding) to the new id. So sessions launched from one checkout and building in separate worktrees never share a gate, a reply log or run markers. `sl orchestrator end` archives the run markers; the run hooks stop.

- `session-start`: injects `using-superlite` at startup, clear and compact. After a compaction (manual, automatic or idle) a session with a run (main or a batch lead; `orchestrator.json`, `backlog.json`, a run marker or `inline-flow.json` in its state folder) also gets the continuation text of `scripts/compact_text.py`: go on from the next step without asking, wait for what still runs, and the run state (`sl status`, plus `sl backlog status` while a batch is not shipped; lines cut at 300 characters, the block at 3,000). If the state cannot be read within 5 seconds the text names `sl status` instead. Off with `SUPERLITE_NO_AUTOCOMPACT=1`. On startup and `/clear` (not in a fleet pane, and not in a folder another live session owns) it also removes the stale nudge stamps (`last-compact`, `last-compact.<sid>`) and the size hint's `compact-hint.<sid>` markers of sessions without a binding from the session's state folder (#466).
- `pre-compact`: on `PreCompact` (auto and manual), for a session with a run (main or a batch lead, not a worker), prints the summary instructions of `scripts/compact_text.py`: keep the user's goal and standing instructions, the decisions, what is in flight and the exact next step; drop tool output and file contents. Claude Code adds this stdout to the compaction request. Static text of about 800 characters; it never blocks a compaction. Off with `SUPERLITE_NO_AUTOCOMPACT=1`.
- `block-unsafe-kill`: always on for Bash and PowerShell; blocks killing processes by name or pattern (`taskkill /IM`, `pkill`, `killall`, `Stop-Process -Name`). Kill by PID is allowed, except for a shared service: `kill [-SIG] PID...` resolves each PID's command with one `ps -p PID -o comm=` call and blocks when its basename matches `Xcode`, `Simulator`, `mcpbridge`, `SourceKitService`, `com.apple.dt.*`, `com.apple.CoreSimulator*`, `herdr`, `claude`, `launchd`, `WindowServer`, `Finder`, `Dock` or `loginwindow` (case-insensitive); the message says to ask the user.
- `block-unsafe-kill` reads only command words (#666): a kill word blocks only at command position (line start, `;`, `&&`, `||`, `|`, `(`, `$(`, a backtick, after a control word such as `if`/`then`/`do`, or after a wrapper such as `env`, `sudo`, `nohup`, `xargs`, `timeout` with its options); text in quotes, comments, heredoc bodies and the arguments of other commands never blocks. The bodies the shell runs are read as commands: `$(...)`, backticks, `<(...)`, `sh -c`, `eval`, `env -S`, `find -exec`, `cmd /c`, `powershell -Command`, and the heredoc or here-string of a stdin shell (`cat <<EOF | sh`). `kill` with the PID `-1` blocks for any signal (`kill -- -1`, `kill -TERM -1`). PowerShell: `kill`/`Stop-Process`/`spps` with `-Name` blocks, a pipe from `Get-Process` without `-Id` blocks, and `Stop-Process -Id` PIDs go to the shared-service check like `kill PID`.
- `block-coordinator-edits`: during a run, blocks the coordinator (calls without `agent_id`) from writing project code; a lead (`SUPERLITE_FLEET_ROLE=lead`) is a coordinator too, and the main checkout's `.superlite/backlog.json` is protected like the other run files, by absolute path, from a worktree and through symlinks (the lead's own `.superlite/` and its state folders stay writable). In every state it blocks writes to `.superlite/orchestrator.json` and `.superlite/human-replies.jsonl`; an interpreter writer in a command that names a protected file is judged by its targets in every state, and a protected or unknown target blocks, as does a move, copy or link API next to it in a command that runs an interpreter, with or without a writer call (`os.replace`, `shutil.*`, `Path.rename`, `fs.rename`, `.copyFileSync(`, and every `.replace(` that does not read as `str.replace`, a quoted first argument and a second). It may write `docs/plans/**`, `docs/*/plans/**`, `SPEC*.md`, `docs/**/*.md`, any `docs.md`, `.superlite/**` and `.git/info/exclude` (the one git metadata file `sl worktree` writes), in the project or in a linked worktree inside it (judged from the worktree's root, as is the human gate's review plan); inline interpreter writes (`python -c`, heredocs, `node -e`) are judged by each writer call's own target (a literal, `Path('...')`, or a name assigned one); every `open(` must be a plain read or such a write, and a writer with an unknown target blocks. Paths with `..` segments count as project code. While the guard enforces, an Edit or Write whose text is allowed still blocks when the target or a parent folder is a symlink whose real path lies outside the allowed set (or cannot be resolved), and when the target is an existing file with more than one hard link. In every state an Edit or Write into the Python cache folder (`~/.cache/superlite`, `$SUPERLITE_CACHE_DIR`) blocks, and the hook uses the cached interpreter only while it is the file `command -v python3` or `command -v python` finds (a planted cache is ignored and the interpreter is probed again). Text inside quoted arguments or heredocs is not an interpreter call, unless a shell runs it (`sh -c`, `eval`, a stdin shell such as `bash <<EOF`, or `$(python ...)`). Bash and PowerShell commands are judged by `skills/subagent-driven-development/scripts/guard_judge.py` (Python; the hook runs it only during a run or when the command names a protected file, any `.superlite` text, or `superlite` together with `python` (the interpreter cache folder), and it fails open on its own errors): it splits the command into simple commands and reads quotes, escapes, `$'...'`, line continuations, comments, redirects before or glued to the command word (`>/dev/null rm`, `rm>/dev/null`, `bash<<<'...'`), heredocs (a heredoc ends only on its exact delimiter line, `<<-` strips leading tabs only) and substitution bodies the way bash does. Relative targets are judged from the effective directory: the input `cwd` when the command holds no `cd` at all; at each `cd` when every `cd` is a plain command into the project and the command is one `&&` chain or a single leading `cd` to an existing folder it may enter, and no command runs `source`, `.`, `eval`, `alias`, `enable` or `trap` (also after redirects, `VAR=value`, `builtin`, `command`, `time` or `exec`, or spelled with quotes or escapes) (interpreter writer targets then from every directory it visits); when the command is lines of `&&` chains (no `|`, `||`, `&`, `!`, parentheses, backticks, control words, `source`, `.`, `eval`, `alias`, `enable` or `trap`, read as for the single chain, no line ending in `&&` or `\`, no `CDPATH` in the command, and with `CDPATH` set only absolute or `./` targets) and every `cd` is a plain `cd DIR` into the project, each command is judged where it runs: after a `cd` in its own `&&` chain from the `cd` target, and after the chain from the target alone when the `cd` is sure, else from the directory before the chain too (interpreter writer targets from every one). Sure: every command before it is `echo`, `printf`, `ls`, `pwd`, `true`, `:`, `cat`, `head`, `tail`, `wc`, `grep`, `test`, `[`, `date`, a `cd` or a `mkdir -p`, none with a redirect into a file (so nothing removed, locked or blocked the folder), and the `cd` starts its chain into an existing folder it may enter, or follows only `mkdir -p` calls (no `-m`) that can succeed and make it (`mkdir -p X && cd X`); otherwise the input `cwd` with each `cd` target judged too when every `cd` is a readable absolute target in the project, a leading `cd <absolute>` to an existing folder it may enter (judged from its target too) or plain relative `cd sub` steps, while any other `cd`, `pushd`, `popd` or `chdir`, a `cd` in a pipe or sent to the background turns the outside base off and judges from the project root, the `cwd` and each `cd` target; a `-c` or substitution body that changes directory is judged from the project root, `env -C` and `sudo -D` (read off their own option words) count as a directory change, relative `cd` steps walk from the input `cwd` (every folder they visit is judged too) and a step into a missing folder leaves the directory unknown, as does a `cd` the guard cannot read (`c''d`, `c\d`, a hidden `pushd`) from there on and, with `CDPATH` set or named in the command, every relative `cd` other than `./DIR`; while the directory is unknown a relative path with `..` blocks, and so does one allowed only by its prefix (`docs/plans/a.md`, `.superlite/x`; `SPEC.md` and `docs.md` pass from any folder), and in every state a relative path ending in a protected file's name counts as that file; the input `cwd` is taken as the shell's own directory (Claude Code's hooks reference: `cwd` follows Claude, "the new directory after Claude runs `cd`"; a `cd` that leaves the allowed directories resets it to the project); so writes outside the project pass; `patch` and `git apply` honour `-d` and `-C` the same way; a writer whose target starts at an absolute path outside the project passes. A stdin shell's program (the heredoc body or here-string of `bash`/`sh` with no `-c` and no script operand, with `-s`, or of `/dev/stdin`; also `source /dev/stdin` and `sudo -s`/`-i` with no command; every heredoc on a line, in order) is judged like a `-c` body, and so is the string of `env -S`; a `-c` or `eval` body that reads stdin as its program (`bash -c "$(cat)"`, `eval "$(cat)"`, `source /dev/stdin`) takes the line's heredocs and here-strings as that program, judged from the project root when the command changes directory anywhere; a heredoc piped into a shell (`cat <<EOF | sh`) is judged as its program, and any other program piped into a shell (`echo ... | bash`) or given by process substitution (`bash <(echo ...)`) is an unknown target, which blocks while the guard enforces and, next to a protected name, in every state. While it enforces, git rewrites of project files block: `git apply`, `git am`, `stash pop|apply|branch`, `reset --hard|--merge|--keep` and the forced discards (`checkout -f`, `switch -f`/`--discard-changes`, `checkout-index -f`/`-a`, `read-tree -u`) in the project, and `checkout`, `restore`, `rm`, `mv` and `clean` on a project path (judged like any write target; a folder, `.` and `clean` with no path stand for what lies in it; `restore --staged`, `rm --cached` and `-n` pass; long options count shortened to a prefix, `--har`, as git takes them; redirects are no paths); `GIT_WORK_TREE` (also through `env` or `export`) and `-c core.worktree` count like `--work-tree`, a `-c alias.X` is judged as what it runs (a `!` alias as a shell command from the project root, where git runs it; an alias of another `-c` alias blocks), an alias from a config the guard cannot read (`-c include.*`, `--config-env`, `GIT_CONFIG*`, `GIT_DIR`, `--git-dir`, or a `git config` in the same command) blocks, and with an unreadable git directory paths are judged from the project root with the directory unknown; an operand glued to a redirect (`src/a.py>/dev/null`) keeps its text; branch moves (`switch`, `checkout <branch>`, `merge`, `rebase`, `pull`) and `git stash` itself pass. `tar -x` and `unzip` block when they extract into project code (the last `-C`, `--directory`, `--cd` or `-d`, read like getopt inside option clusters, else the shell's directory; tar joins a relative `-C` onto the one before it, and every `-C` that member names follow is judged too; tar long options count shortened to a prefix, `--ext`, `--dir=`, and the value of one such as `--file X`, `--strip-components N` or `-I PROG` is no member name), and absolute member names (`tar -P`) block; extraction to stdout (`-O`) passes; of the other archivers, `7z x`/`e` (also `7za`, `7zr`, `7zz`) is judged by its `-o` folder (else the shell's directory), `cpio -i`/`-p` is an unknown target and `ditto` is out of reach. `nohup`, `timeout`, `nice` and `exec` are skipped like `sudo` and `env`, with their own options. The guard is best-effort: it judges `-c`, stdin-shell, `eval` and substitution bodies beyond one level, up to 8 levels deep (a deeper body is an unknown target), and does not parse every shell form. Accepted limits: the judge has a step and time budget (no quadratic growth with the number of quoted words, no fail-open timeout), and a command that exceeds it (very many quoted words, nested quotes inside a `$(...)` within double quotes) is an unknown target: it blocks while the guard enforces and, next to a protected name, in every state; it does not fail open. `sed`/`perl` `-i` (also inside a flag cluster) judge every file operand; `ruby` and `php` writers count as interpreter writers. Subagents always pass. A block of project code (not the protected-file block, which has no such line) ends with the judged item on the last stderr line: `Blocked target: <project-relative path>` for a write, `Blocked command: <command>` when the command itself was judged. A folder `rm -r` or `rmdir` of project code blocks unless the folder holds only untracked, unowned single-link files; every block of a command prints a `Refused command:` line naming the command it came from (none of that Bash call ran), and a Python string composed with `+` is read as its joined value. Arithmetic is no command, redirect or heredoc: `$(( ))`, a `(( ))` command and a `for (( ))` header only run the `$(...)`, backtick and `${...}` substitutions inside them (when the first `)` at depth 0 is not followed by `)`, bash's substitution or group reading stands). In Python code (`python -c`, a heredoc program, a script the command wrote) a writer call inside a string literal (also an f-string's literal text; its `{...}` fields are code) or a comment is data, unless the code can run text (`exec`, `eval`, a bare `compile`, `__import__`, `getattr`, `system`, `popen`, `builtins`, `runpy`, `importlib`, `subprocess`, `os.system`/`popen`/`exec*`/`spawn*`, also imported with `from os import` or called on any receiver, a `.exec(` or `.eval(` method call, `timeit`, `cProfile`, `profile`, `pdb`, `doctest`, `asyncio.create_subprocess_*`, `globals`, `vars`, `locals`, `sys.modules`, `__dict__`, `__globals__`, `__subclasses__`, `operator`, `pty`, `pickle`, `marshal`, `ctypes`, the `code` module, `sys.path`, `chdir`, `imp`, `zipimport`, `pkgutil`, `site`) or cannot be tokenized; a parameter of a module-level function (only while strings are data; defined once, no `*args`, `**kwargs`, positional-only or keyword-only parameters, its name used only in direct calls) stands for the literals its calls pass. A function with a decorator binds nothing. The runner list is best effort: the guard stops a coordinator's mistakes and is no sandbox against code written to get past it. `tempfile.mkdtemp()` and `tempfile.TemporaryDirectory()` (no `dir`; at most a literal prefix and suffix without a slash, a backslash or `..`; the latter also takes `ignore_cleanup_errors` and `delete`) are a new folder below the temp root (`TemporaryDirectory` as `with ... as NAME`, as `.name` on the call, and as `NAME.name` after `NAME = tempfile.TemporaryDirectory()` while every other use of NAME is a `.name` read or `.cleanup()`, with no second binding, no write to `NAME.name` in any form (assignment, list or parenthesised target, annotation, `del`, `for`, `with`) and no `setattr`; the code is read as a syntax tree) and `tempfile.gettempdir()` the temp root (the hook's own, like `$TMPDIR`), unless the command names `TMPDIR`, `TEMP`, `TMP` or `tempdir` other than as `$TMPDIR` or `${TMPDIR}` (likewise `$TEMP`, `$TMP`); `from tempfile import mkdtemp` is not read. An inline build (the run's plan in `stable.json` holds exactly one task, no `**Repo:**`) may also write that task's Owns: Bash targets through the judge, an Edit or Write through `guard_judge.py --owns PATH`, run only for a path the hook would block; protected names, hard links and paths outside the plan root still block. A target written exactly `$(git rev-parse --git-path info/exclude)` or `$(git rev-parse --git-common-dir)/info/exclude` (or the backtick form) passes as git's own exclude file, unless the command names any `GIT_` variable, sets `PATH`, defines a `git` function or alias, or holds `$(` or a backtick inside single quotes; then it is an unknown target. The fleet block (rule 4) follows `moved_to` up to 5 hops and ends with `Fleet state read: <folder>/fleet.json` (plus `, moved to <folder>/fleet.json`).
- `block-coordinator-edits`, git-ignored paths (#664): a literal target from one known folder passes as an `rm`, `rmdir` or `unlink` target, and as a redirect or any non-git writer target (`tee`, `cp`, `mv`, `sed -i`, `ln`, `install`, `rsync`, an interpreter's write), when git does not track it (`git ls-files`), no task Owns it, and `git check-ignore -v` names a non-negated pattern in a tracked `.gitignore` of the work tree (`.git/info/exclude`, `core.excludesFile`, the global ignore file, an untracked `.gitignore` and `!` patterns never count), whatever its size, symlinks or link count. Kept: `.git`, `.superlite` and run-file names, a hard-linked file as a write target, a folder that holds a linked worktree of the project or a state folder of the run, a glob target, and a run with no readable plan. A path git does not ignore keeps today's rule for `rm` (untracked, single-link files, at most 2000 entries) and blocks as a write. Also kept: any path whose part below its innermost work tree root (the project, or a linked worktree inside it) is `.claude` or starts with `.claude/` (`.claude settings keep their own rules`). The housekeeping git calls share the judge's deadline (none runs once it has passed: `git could not tell`), and the worktree list and each `.gitignore` source's tracked answer are asked once per call. A block of such a target prints `Not housekeeping: <why>` right after the `Refused command:` line.
- `block-coordinator-edits`, variables (#665): `$HOME` and `${HOME}` read like `~` (the hook's own `HOME` when it is absolute; unset, empty or relative stays an unknown word, and an assigned `HOME=` wins). A double-quoted expansion is one word, so a variable's value with spaces resolves there; unquoted it stays unknown, as bash would split it. `perl -e 'alarm N; exec @ARGV' CMD` (also `-E`, `alarm shift`, `exec(@ARGV)`) is judged as `CMD`; `system @ARGV` is not (one `--` after the code is dropped; a next word that starts with `-` is a perl switch and keeps the perl-code reading; one word left is judged as `sh -c WORD`). A known name set only for one command (`HOME=x cmd`, `env HOME=x cmd`: HOME, TMPDIR, PWD, CLAUDE_PROJECT_DIR, IFS) is unknown in that command's `-c`, `eval`, `source` and stdin bodies. A `git config` or git dir named only in a read-only command's arguments (a `grep` pattern) no longer makes git's config unreadable, and an unknown git target names its token: `? (from git: <sub>: no git command, read as an alias while the command names git config)`.
- `block-coordinator-edits`, scratch folder (#690): `<state folder>/scratch/` (normally `.superlite/scratch/`) is the coordinator's place for a throwaway script (count lines, compare outputs, time a command). Writes there pass like any `.superlite/**` path; the folder is git-ignored with `.superlite/` and `sl orchestrator end` removes it. While the guard enforces (an active run or an unapproved human plan), a Bash command that names a script there by its file name (a `.py`, `.sh`, `.bash`, `.zsh`, `.js`, `.mjs`, `.cjs`, `.ts`, `.pl`, `.rb` or `.php` file, or an executable one; regular files, no symlinks, in the folder and one level below, at most 64 files and 65536 characters each) reaches the judge with that script's text as a heredoc in front of the command, so a script written in an earlier call is judged like one the command writes itself: one that only reads the project passes, one that writes project code is blocked. The code block's message names the folder.
- `block-coordinator-edits`, session scripts and eval (#693): while the guard enforces, a run of a script file is judged by the file's text when this session wrote it: an interpreter's script operand (`sh`, `bash`, `zsh`, `ksh`, `dash`, `python`, `pypy`, `node`, `bun`, `perl`, `ruby`, `php`), `uv run X.py`, a path run as a command (`./x.sh`, `/tmp/x.py`; the language from its `#!` line, a file without one is a shell script), `source`/`.` and a shell or Python reading the file on stdin (`sh < x.sh`). A file is this session's when it lies in `<state folder>/scratch/`, or when git does not track it in its own repository, it lies outside the superlite plugin (unless inside the project), and it changed at or after the session start (the earlier of the transcript's birth time and its first `timestamp`; without either every such file counts). A file the guard cannot read blocks and names why (over 65536 characters, not UTF-8, a read error, a `#!` interpreter it cannot judge); a binary (a NUL byte, an ELF, Mach-O or PE header) is no script and runs; a missing file or an operand with an unresolved variable runs as before. A script written earlier in the same call is matched from every directory the command may be in (`cd .superlite/scratch && python3 m.py`, `uv run m.py`), and in a judged Python script `__file__` is the script's path (`Path(__file__).parent`, `os.path.dirname`, `abspath`, `realpath`). `eval` judges the text it runs: `$(echo ...)` and `$(printf ...)` with literal words and the variables the command assigned resolve; any other substitution or variable is an unknown target, except `$(cat)` and the other stdin forms, which take the heredocs, and `$(ssh-agent ...)`. Unquoted `$CLAUDE_PROJECT_DIR`, `$PWD` and `$TMPDIR` whose value holds a space, tab or newline stay unknown, like `$HOME`. The judge's code block prints the scratch-folder line itself.
- `block-coordinator-edits`, subprocess arguments (#705): in a script the guard judges (inline code, a heredoc, a scratch or session script), a `subprocess`, `os.system` or `os.popen` call whose argument list starts with a string literal is judged by that program and its literal words; a word that is not a string literal reads like an unknown shell variable, so `subprocess.run(["git", "show", f"HEAD:{p}"])` passes as `git show "$x"` does and `subprocess.run(["cp", "a", p])` stays unknown. A Python name bound only to one literal, and a `+`, `os.path.join` or `str()` of literals, count as that literal. Unknown: a program that is not a string literal (`[prog, ...]`, `run(cmd)` unless #780 reads `cmd`, an f-string or `+` shell string), an unpacked list the guard cannot read or a `+` tail (`["bash", *args]`, `["git"] + rest`), and, in these calls and in shell strings inside scripts, a non-literal word before the last word of a shell or interpreter, an interpreter's inline code that is not a literal, any non-literal word of `find`, and a wrapper (`env`, `timeout`, `sudo`) whose program word is not a literal. The block names the cause: `Unresolved word: ? (from python3: subprocess program is not a string literal)` or `... subprocess argument N is not a string literal` (the program is argument 1). Other languages' comma-form calls (`system("git", "show", rev)`) stay unknown for a later non-literal argument.
- `block-coordinator-edits`, unresolved words (#780, #781): `source <(...)` and `. <(...)` pass when the substitution is one print-only `sed -n` (each script only `p` with optional line-number, `$` or `/regex/` addresses), `cat`, `head` or `tail` whose operands are literal, existing, git-tracked regular files outside `<state folder>/scratch/` that the call did not write (also not below a folder it wrote), like `source <tracked file>`, while no `source`, `.` or `eval` ran earlier in the call; any other `<(...)` stays an unknown target. A script made by `cp` or `mv` (options only `-f`, `-p`, `-v`, `-a`) of one literal source (also into a folder, one an earlier `mkdir` of the call made too) is judged by the source's text when the same call runs it, if the source is a single-link regular file (no symlink) the call did not write, also not below a folder it wrote, and the copy cannot fail on a read-only destination; otherwise its run is an unknown target; any other later write to a heredoc-written script (by its path, its real path or a folder above it; `cat >>` appends to the text) drops its text, so its run is an unknown target. After a link-making command (`ln`, `link`, or `cp`/`install` with a link option) the call keeps no script text, and neither the copy rule nor the print-only `source <(...)` pass applies; these paths are compared case-folded. A `for` list word `$(seq [FIRST [STEP]] LAST)` with integer operands or a numeric `{A..B}` binds its numbers (at most 64; not when the command defines a `seq` function or alias, assigns `PATH` or sets `IFS`). In a judged script a list name bound once to a literal list or tuple (every other use a subprocess call's argument or a `*` splat in a list) counts as that list, a `*` splat of such a list or of a literal one is flattened, and `sys.executable` (after `import sys`, never assigned) reads as `python3`; none of these reads hold when the code can rebind names another way (`setattr`, `getattr`, `delattr`, a dunder attribute, `__main__`, `builtins`, `inspect`, `importlib`, `gc`, `ctypes`, `sys.modules`, `f_globals`, a `match` pattern), or calls `subprocess` through a name it does not import once; with `shell=True` the list's first word is judged as shell text. An unresolved block names the way out for its cause: a `<(...)` program (write it to `<scratch>/defs.sh` in one call, then `. <scratch>/defs.sh` in the next), an `eval` the guard cannot read (print it, then run the printed command literally) and too many variable values (write the words literally; `sl commit_task Tn --also A B C` takes several paths). A `for`, `while`, `until`, `if` or `select` block that a `&&` chain reaches after a `cd X` judges its body from X alone, as the plain command after the `cd` is; the folders the chain could have left the shell in count again after the block's `done` or `fi`, and no `cd` becomes sure by this.
- `block-coordinator-edits`, unknown option words (#727): some words may stand where an option of `sed`, `perl`, `cp`, `mv`, `ln`, `install`, `rsync` or `tar` can (before `--`; for perl, only its first operand). Such a word counts as unknown when the guard cannot read it: a non-literal word in a script, or in the Bash walk a word whose first character, or the option name before `=`, comes from an unread expansion. An unknown word counts as a possible bare option that writes: sed and perl `-i` (with `-e` from a second such word), cp, mv, ln and install `-t`, cp `-s`, install `-d`, rsync `--remove-source-files`. The guard judges the command as written and with each such word read as each of those options, alone and in pairs, and blocks when any reading writes a protected path. More than 8 such words gives an unknown target. A tar word of that kind may be `-x` and `-P`, so it gives an unknown target, unless the command gives a literal mode other than extract: `c`, `t`, `r`, `u`, `A` or `d`, or a long mode spelled out whole such as `--create`. So `sed "$F" s/a/b/ src/a.py`, `cp "$F" src x` and `tar "$F" -f a.tar` block, while `sed -n "${A},${B}p" src/a.py`, `sed -n '$p' a b`, `cp "$f" /tmp/x/` and `tar -czf out.tgz "$d"` pass. An option whose value sits inside the unknown word (`--target-directory=D`, `-e 'w FILE'`) is not read.
- `block-coordinator-edits`, unknown git words (#726, #728, #749): a `git checkout` operand that is not a literal is an unknown target (`Unresolved word: ? (from git: checkout operand $x may be a path; git switch takes only a branch)`) unless `--`, `-b`, `-B`, `--orphan` or `--detach` is given, and so is a git subcommand that is not a literal (`subcommand $s is not a literal`). A Python subprocess call's literal `cwd=` folder resolves its relative targets; an unknown one (not a literal, empty, `~`-prefixed) makes them unknown, `subprocess cwd= is not a string literal`. An unknown word where a git option may stand (after the subcommand, before `--`, not the value of an option such as `-b` or `switch -c`; read as for #727) counts as the subcommand's writing flag: reset `--hard`, switch and checkout `-f`, restore `-W`, read-tree `-u`, checkout-index `-a`; the targets are the union with the command as written. A reading git would refuse is not read: switch with no branch operand left (unless `-c`, `-C`, `--orphan` or `--detach` is given), reset after a literal `--soft` or `--mixed` or with paths after `--`, checkout with paths after `--`; nor is `--output` of `diff`, `log` or `show`. So `git restore --staged "$o" src/a.py`, `git switch "$o" main`, `git reset "$o"` and `git checkout -b n "$o"` block, while `git switch "$b"`, `git checkout -b "$b"`, `git reset --soft "$c"`, `git restore --staged "$f"` and `git log "$range"` pass.
- `block-coordinator-edits`, fleet on (rule 4, #710): while `.superlite/fleet.json` says on, an in-process Agent call of a superlite role (`implementer`, `implementer-haiku`, `fixer-sonnet`, `fixer-sonnet-high`, `fixer-opus`, `package-reviewer`, `final-reviewer`, `researcher`, `checker`, `writer`; any letter case, with or without `superlite:`) is refused with its `sl fleet spawn --role` line and a `rule-block` row in `incidents.jsonl`; the writer's line names `sl fleet spawn --role writer --brief <abs brief file> --plan PLAN`, whose `Output:` line names the one file the writer may write.
- `block-coordinator-edits`, fleet backlog guard (#706): in a fleet session a heredoc body or quoted text counts as runnable when another command of the Bash call is a runner, unless it is written data, which needs all of: (1) it is not inside `$( )` or backticks; (2) its consumer's command word (the simple command the quote belongs to, or whose `<<` opened the heredoc; reserved words and `NAME=value` skipped) is `cat`, `tee`, `printf` or `echo`; (3) that command redirects stdout with `>` or `>>` (no fd, or fd 1) to a file, not `&N` and not `>(...)`; (4) every written file (each redirect target, plus each `tee` operand) is plain: no `$`, backtick, `*`, `?` or `[`, and not under `/dev/` or `/proc/` except `/dev/null`; (5) no other command of the call runs a written file: none whose command word is the file's basename (`./f.sh`), no runner command with a word containing the basename (`bash f.sh`, `bash < f`, `python3 /tmp/x.py`), no command inside `$( )` or backticks with a word containing the basename when the call holds a runner (`eval "$(cat f.md)"`; a top-level `git add f.md && make test` is no run), and no `make` in the call when the basename is a makefile (`Makefile`, `makefile`, `GNUmakefile`, `*.mk`). Passes: `cat > docs/x.md <<'EOF' ... EOF` then `make test`; `echo 'text' >> notes.md; node build.js`. Stays blocked: `bash <<'EOF'`, `cat <<'EOF' | bash`, `cat > f.sh <<'EOF' ... EOF` then `bash f.sh`, `git commit -m '...' && make test`, an unquoted heredoc holding `$(` or a backtick. The block line gains a `Matched:` sentence naming the heredoc (`<<DELIM`) or the quoted text and why it counts (the runner in its own command, a written file the call runs, or the runner word elsewhere in the call, with the advice to write the file in one Bash call and run it in another). A file a runner reads by convention other than a makefile (`package.json`, `conftest.py`) is not traced; the backlog script's own fleet-worker refusal is the backstop.
- `mark-inline-flow`: on a `/superlite:small` or `/superlite:debug` prompt and when `superlite:test-driven-development` or `superlite:systematic-debugging` is loaded (the implement-phase skills; brainstorming alone writes nothing), writes `<state folder>/inline-flow.json` `{"flow": "small|debug|tdd|debugging", "at": <epoch>, "inplace": null | "<reason>"}`. `sl orchestrator end` and a new session start clear it.
- `inline-worktree-guard`: while `inline-flow.json` exists, refuses an Edit, Write or NotebookEdit of a path inside the main checkout (not below a linked worktree, not under `.superlite/` or `.claude/`); run `sl worktree ensure <topic>` and work in the folder it prints. `sl worktree inplace --reason TEXT` records an opt-out for a trivial change (the reason goes to `.superlite/progress.md`) and the edit then passes. Subagents and fleet workers are exempt; a plan run (run marker) is left to `block-coordinator-edits`.
- `record-human-reply`: a lead counts as a coordinator, so its prompts are logged like main's; while the session's state is human and unapproved, appends each human prompt to `.superlite/human-replies.jsonl` (the evidence `sl orchestrator approve` checks).
- `rewrite-test-runs`: during a run, rewrites the coordinator's (or a lead's) raw test commands (pytest, npm test, go test, cargo test, dotnet test, ...) into a background `sl run_tests`: named test paths go to `--fast`, a bare runner to `--full`; a pytest `-m EXPR` (a word or one quoted string) stays on the rewritten command; it logs a `rule-rewrite` incident (with `target` `<original> -> <rewritten>`, `rule raw-test-run`, `cwd`, `command` and `rewritten`). It denies a known runner inside `until` or `while`, a test run sent to `/dev/null`, a subagent's bare full suite (a named file passes), and a subagent's or fleet worker's run of the configured test command on an isolate stack (the message gives `sl run_tests --fast ... --task Tn --background`). A coordinator test command with a quoted argument (`"` or `'`) passes unchanged; for a subagent a quoted file name counts as a named file, a quoted flag value (`-m "not slow"`) does not. A test run outside the plan root (the payload cwd, then each `cd`/`pushd`; a cwd above the plan root, such as the main checkout of a linked worktree, counts as inside), in a directory the hook cannot read (a variable, `cd -`, `popd`), or naming an absolute or `..` path outside it, is left as written with no rewrite and no denial; a redirect target is never a test path.
- `capture-worker-stop`: on a fleet worker's stop, writes the stop record into the run folder `SUPERLITE_FLEET_PARENT_DIR` names (the main `.superlite` for a lead), so `fleet_io.latest_stop` and `wait` find it.
- `deny-worker-permission`: in a fleet pane (`SUPERLITE_FLEET_WORKER` set), answers a permission dialog with no, so a worker never waits on a prompt.
- `compact-nudge`: on `UserPromptSubmit`, for a main session with a run, when the last main-conversation request in the transcript was above 500k tokens (so no auto-compact window is active; with one, Claude Code would have compacted), adds one context line asking the agent to tell the user to run `/autocompact 400k` or `sl setup`; shown once per session (it marks `.superlite/compact-hint.<session_id>`; `session-start` removes the marker once the session is neither the starting one nor bound). Silent in fleet panes. Off with `SUPERLITE_NO_AUTOCOMPACT=1`.

## Detecting an active run

For a third-party hook, use the first of these that applies (the order of `hooks/superlite-state.sh` and `state.py`). 1. `SUPERLITE_STATE_DIR`, when set, is the `.superlite` folder. 2. Read `session_id` from the hook input and read the first line of `~/.superlite/sessions/<session_id>` (`$SUPERLITE_HOME/sessions/<session_id>` when `SUPERLITE_HOME` is set) as the bound `.superlite` folder; it counts while the folder exists and its `session` file is empty or names this session (another name means taken over). 3. Legacy: `<project>/.superlite` (`CLAUDE_PROJECT_DIR`, else the input `cwd`), unless its `session` file names another live session whose binding points at that folder. No such file or folder means no bound run. A run is active while that folder holds `pool.json`, `prime.md` or `stable.json`. `sl orchestrator end` archives those markers.

Warning: checkpoint mode leaves the tree dirty during a run by design, so a Stop hook that polices uncommitted files should stay silent while a run is active.

`sl run active [--json] [--plan P] [--session SID]` (`<plugin root>/skills/subagent-driven-development/scripts/sl`) does this resolution in one call (a hook passes its input's `session_id` as `--session`): exit 0 while a run is active, 1 when none. Run markers beyond the three above: `orchestrator.json` and `inline-flow.json` (also archived by `sl orchestrator end`); `backlog.json` counts while one of its batches is `running` or `needs_decision` (kind `backlog main`), and a folder whose checkout is such a batch's worktree is a `lead`; a busy pool agent or fleet worker also counts (kind `plan run`). `--json` prints one document: `active`, `kind`, `state_dir`, `markers`, `batch`, `worktrees` (the folder's checkout first, then each running batch's worktree, each with `path`, `batch`, `state` and the `busy` worker ids), `checkpoint_files` (files the hidden checkpoints already hold unchanged; a hook can leave them out of its warning) and `edited_after_checkpoint` (changed since; still uncommitted work).
