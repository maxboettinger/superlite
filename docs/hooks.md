# Hooks

`hooks/hooks.json` registers these. The run hooks are active only while a run marker exists (`.superlite/stable.json`, `prime.md` or `pool.json`, written by the first lint). They fail open on bad input.

**Which `.superlite`.** Each session has its own (`hooks/superlite-state.sh`, the same order as `scripts/state.py`): `$SUPERLITE_STATE_DIR`; else the session's binding `~/.superlite/sessions/<session_id>`, written by `sl orchestrator set|approve|bind` and `lint --stable`; else `<CLAUDE_PROJECT_DIR or cwd>/.superlite`, unless its `session` file names another live session (one whose binding points at it). A binding counts only while no other session took the folder over: `sl orchestrator bind --force`, or without `--force` a session launched in the folder's own project (line 3 of a binding records the launch directory) when the owner was launched elsewhere, as a build session launched in a worktree takes over the planning session's folder; an owner launched in the same directory still wins. `session-start` exports the hook's id as `SUPERLITE_SESSION_ID` (through `CLAUDE_ENV_FILE`), so `sl` binds under the id the hooks read; on `/clear` it hands the one binding of the same Claude process (`CLAUDE_PID`, line 2 of the binding) to the new id. So sessions launched from one checkout and building in separate worktrees never share a gate, a reply log or run markers. `sl orchestrator end` archives the run markers; the run hooks stop.

- `session-start`: injects `using-superlite` at startup, clear and compact.
- `block-unsafe-kill`: always on for Bash and PowerShell; blocks killing processes by name or pattern (`taskkill /IM`, `pkill`, `killall`, `Stop-Process -Name`). Kill by PID is allowed, except for a shared service: `kill [-SIG] PID...` resolves each PID's command with one `ps -p PID -o comm=` call and blocks when its basename matches `Xcode`, `Simulator`, `mcpbridge`, `SourceKitService`, `com.apple.dt.*`, `com.apple.CoreSimulator*`, `herdr`, `claude`, `launchd`, `WindowServer`, `Finder`, `Dock` or `loginwindow` (case-insensitive); the message says to ask the user.
- `block-coordinator-edits`: during a run, blocks the coordinator (calls without `agent_id`) from writing project code; a lead (`SUPERLITE_FLEET_ROLE=lead`) is a coordinator too, and the main checkout's `.superlite/backlog.json` is protected like the other run files, by absolute path, from a worktree and through symlinks (the lead's own `.superlite/` and its state folders stay writable). In every state it blocks writes to `.superlite/orchestrator.json` and `.superlite/human-replies.jsonl`; an interpreter writer in a command that names a protected file is judged by its targets in every state, and a protected or unknown target blocks, as does a move, copy or link API next to it in a command that runs an interpreter, with or without a writer call (`os.replace`, `shutil.*`, `Path.rename`, `fs.rename`, `.copyFileSync(`, and every `.replace(` that does not read as `str.replace`, a quoted first argument and a second). It may write `docs/plans/**`, `docs/*/plans/**`, `SPEC*.md`, `docs/**/*.md`, any `docs.md`, `.superlite/**` and `.git/info/exclude` (the one git metadata file `sl worktree` writes), in the project or in a linked worktree inside it (judged from the worktree's root, as is the human gate's review plan); inline interpreter writes (`python -c`, heredocs, `node -e`) are judged by each writer call's own target (a literal, `Path('...')`, or a name assigned one); every `open(` must be a plain read or such a write, and a writer with an unknown target blocks. Paths with `..` segments count as project code. While the guard enforces, an Edit or Write whose text is allowed still blocks when the target or a parent folder is a symlink whose real path lies outside the allowed set (or cannot be resolved), and when the target is an existing file with more than one hard link. In every state an Edit or Write into the Python cache folder (`~/.cache/superlite`, `$SUPERLITE_CACHE_DIR`) blocks, and the hook uses the cached interpreter only while it is the file `command -v python3` or `command -v python` finds (a planted cache is ignored and the interpreter is probed again). Text inside quoted arguments or heredocs is not an interpreter call, unless a shell runs it (`sh -c`, `eval`, a stdin shell such as `bash <<EOF`, or `$(python ...)`). Bash and PowerShell commands are judged by `skills/subagent-driven-development/scripts/guard_judge.py` (Python; the hook runs it only during a run or when the command names a protected file, any `.superlite` text, or `superlite` together with `python` (the interpreter cache folder), and it fails open on its own errors): it splits the command into simple commands and reads quotes, escapes, `$'...'`, line continuations, comments, redirects before or glued to the command word (`>/dev/null rm`, `rm>/dev/null`, `bash<<<'...'`), heredocs (a heredoc ends only on its exact delimiter line, `<<-` strips leading tabs only) and substitution bodies the way bash does. Relative targets are judged from the effective directory: the input `cwd` when the command holds no `cd` at all; at each `cd` when every `cd` is a plain command into the project and the command is one `&&` chain or a single leading `cd` to an existing folder it may enter, and no command runs `source`, `.`, `eval`, `alias`, `enable` or `trap` (also after redirects, `VAR=value`, `builtin`, `command`, `time` or `exec`, or spelled with quotes or escapes) (interpreter writer targets then from every directory it visits); when the command is lines of `&&` chains (no `|`, `||`, `&`, `!`, parentheses, backticks, control words, `source`, `.`, `eval`, `alias`, `enable` or `trap`, read as for the single chain, no line ending in `&&` or `\`, no `CDPATH` in the command, and with `CDPATH` set only absolute or `./` targets) and every `cd` is a plain `cd DIR` into the project, each command is judged where it runs: after a `cd` in its own `&&` chain from the `cd` target, and after the chain from the target alone when the `cd` is sure, else from the directory before the chain too (interpreter writer targets from every one). Sure: every command before it is `echo`, `printf`, `ls`, `pwd`, `true`, `:`, `cat`, `head`, `tail`, `wc`, `grep`, `test`, `[`, `date`, a `cd` or a `mkdir -p`, none with a redirect into a file (so nothing removed, locked or blocked the folder), and the `cd` starts its chain into an existing folder it may enter, or follows only `mkdir -p` calls (no `-m`) that can succeed and make it (`mkdir -p X && cd X`); otherwise the input `cwd` with each `cd` target judged too when every `cd` is a readable absolute target in the project, a leading `cd <absolute>` to an existing folder it may enter (judged from its target too) or plain relative `cd sub` steps, while any other `cd`, `pushd`, `popd` or `chdir`, a `cd` in a pipe or sent to the background turns the outside base off and judges from the project root, the `cwd` and each `cd` target; a `-c` or substitution body that changes directory is judged from the project root, `env -C` and `sudo -D` (read off their own option words) count as a directory change, relative `cd` steps walk from the input `cwd` (every folder they visit is judged too) and a step into a missing folder leaves the directory unknown, as does a `cd` the guard cannot read (`c''d`, `c\d`, a hidden `pushd`) from there on and, with `CDPATH` set or named in the command, every relative `cd` other than `./DIR`; while the directory is unknown a relative path with `..` blocks, and so does one allowed only by its prefix (`docs/plans/a.md`, `.superlite/x`; `SPEC.md` and `docs.md` pass from any folder), and in every state a relative path ending in a protected file's name counts as that file; the input `cwd` is taken as the shell's own directory (Claude Code's hooks reference: `cwd` follows Claude, "the new directory after Claude runs `cd`"; a `cd` that leaves the allowed directories resets it to the project); so writes outside the project pass; `patch` and `git apply` honour `-d` and `-C` the same way; a writer whose target starts at an absolute path outside the project passes. A stdin shell's program (the heredoc body or here-string of `bash`/`sh` with no `-c` and no script operand, with `-s`, or of `/dev/stdin`; also `source /dev/stdin` and `sudo -s`/`-i` with no command; every heredoc on a line, in order) is judged like a `-c` body, and so is the string of `env -S`; a `-c` or `eval` body that reads stdin as its program (`bash -c "$(cat)"`, `eval "$(cat)"`, `source /dev/stdin`) takes the line's heredocs and here-strings as that program, judged from the project root when the command changes directory anywhere; a heredoc piped into a shell (`cat <<EOF | sh`) is judged as its program, and any other program piped into a shell (`echo ... | bash`) or given by process substitution (`bash <(echo ...)`) is an unknown target, which blocks while the guard enforces and, next to a protected name, in every state. While it enforces, git rewrites of project files block: `git apply`, `git am`, `stash pop|apply|branch`, `reset --hard|--merge|--keep` and the forced discards (`checkout -f`, `switch -f`/`--discard-changes`, `checkout-index -f`/`-a`, `read-tree -u`) in the project, and `checkout`, `restore`, `rm`, `mv` and `clean` on a project path (judged like any write target; a folder, `.` and `clean` with no path stand for what lies in it; `restore --staged`, `rm --cached` and `-n` pass; long options count shortened to a prefix, `--har`, as git takes them; redirects are no paths); `GIT_WORK_TREE` (also through `env` or `export`) and `-c core.worktree` count like `--work-tree`, a `-c alias.X` is judged as what it runs (a `!` alias as a shell command from the project root, where git runs it; an alias of another `-c` alias blocks), an alias from a config the guard cannot read (`-c include.*`, `--config-env`, `GIT_CONFIG*`, `GIT_DIR`, `--git-dir`, or a `git config` in the same command) blocks, and with an unreadable git directory paths are judged from the project root with the directory unknown; an operand glued to a redirect (`src/a.py>/dev/null`) keeps its text; branch moves (`switch`, `checkout <branch>`, `merge`, `rebase`, `pull`) and `git stash` itself pass. `tar -x` and `unzip` block when they extract into project code (the last `-C`, `--directory`, `--cd` or `-d`, read like getopt inside option clusters, else the shell's directory; tar joins a relative `-C` onto the one before it, and every `-C` that member names follow is judged too; tar long options count shortened to a prefix, `--ext`, `--dir=`, and the value of one such as `--file X`, `--strip-components N` or `-I PROG` is no member name), and absolute member names (`tar -P`) block; extraction to stdout (`-O`) passes; of the other archivers, `7z x`/`e` (also `7za`, `7zr`, `7zz`) is judged by its `-o` folder (else the shell's directory), `cpio -i`/`-p` is an unknown target and `ditto` is out of reach. `nohup`, `timeout`, `nice` and `exec` are skipped like `sudo` and `env`, with their own options. The guard is best-effort: it judges `-c`, stdin-shell, `eval` and substitution bodies beyond one level, up to 8 levels deep (a deeper body is an unknown target), and does not parse every shell form. Accepted limits: the judge has a step and time budget (no quadratic growth with the number of quoted words, no fail-open timeout), and a command that exceeds it (very many quoted words, nested quotes inside a `$(...)` within double quotes) is an unknown target: it blocks while the guard enforces and, next to a protected name, in every state; it does not fail open. `sed`/`perl` `-i` (also inside a flag cluster) judge every file operand; `ruby` and `php` writers count as interpreter writers. Subagents always pass. A block of project code (not the protected-file block, which has no such line) ends with the judged item on the last stderr line: `Blocked target: <project-relative path>` for a write, `Blocked command: <command>` when the command itself was judged.
- `mark-inline-flow`: on a `/superlite:small` or `/superlite:debug` prompt and when `superlite:test-driven-development` or `superlite:systematic-debugging` is loaded (the implement-phase skills; brainstorming alone writes nothing), writes `<state folder>/inline-flow.json` `{"flow": "small|debug|tdd|debugging", "at": <epoch>, "inplace": null | "<reason>"}`. `sl orchestrator end` and a new session start clear it.
- `inline-worktree-guard`: while `inline-flow.json` exists, refuses an Edit, Write or NotebookEdit of a path inside the main checkout (not below a linked worktree, not under `.superlite/` or `.claude/`); run `sl worktree ensure <topic>` and work in the folder it prints. `sl worktree inplace --reason TEXT` records an opt-out for a trivial change (the reason goes to `.superlite/progress.md`) and the edit then passes. Subagents and fleet workers are exempt; a plan run (run marker) is left to `block-coordinator-edits`.
- `record-human-reply`: a lead counts as a coordinator, so its prompts are logged like main's; while the session's state is human and unapproved, appends each human prompt to `.superlite/human-replies.jsonl` (the evidence `sl orchestrator approve` checks).
- `rewrite-test-runs`: during a run, rewrites the coordinator's (or a lead's) raw test commands (pytest, npm test, go test, cargo test, dotnet test, ...) into a background `sl run_tests`: named test paths go to `--fast`, a bare runner to `--full`; it logs a `rule-rewrite` incident. It denies a known runner inside `until` or `while`, a test run sent to `/dev/null`, a subagent's bare full suite (a named file passes), and a subagent's or fleet worker's run of the configured test command on an isolate stack (the message gives `sl run_tests --fast ... --task Tn --background`). A coordinator test command with a quoted argument (`"` or `'`) passes unchanged; for a subagent a quoted file name counts as a named file, a quoted flag value (`-m "not slow"`) does not.
- `capture-worker-stop`: on a fleet worker's stop, writes the stop record into the run folder `SUPERLITE_FLEET_PARENT_DIR` names (the main `.superlite` for a lead), so `fleet_io.latest_stop` and `wait` find it.
- `deny-worker-permission`: in a fleet pane (`SUPERLITE_FLEET_WORKER` set), answers a permission dialog with no, so a worker never waits on a prompt.
- `compact-nudge`: on `UserPromptSubmit`, when the session is 30 minutes past its launch or last compact, adds one context line asking the agent to tell the user to run `/compact`; shown once per window (it stamps `.superlite/last-compact.<session_id>`, per session; `session-start` resets it on `/compact`). Off with `SUPERLITE_NO_AUTOCOMPACT=1`.
- `capture-agent-launch`: during a run, appends a `launch` record (agent id, type, model, description) to `.superlite/metrics.jsonl` after each `Agent` call.
- `capture-agent-stop`: during a run, appends a `stop` record (agent id, type, transcript path, last message) to `.superlite/metrics.jsonl` when a subagent stops.
- `final-review-check`: on `Stop`, blocks once per branch (recorded in `.superlite/final-review-warned`) when the branch is not the default branch (`origin/HEAD`, else `main`, else `master`; detached HEAD is ignored), changes 5 or more files or 150 or more lines against the merge-base, working tree and untracked files included (`docs/` and `.superlite/` excluded; untracked files over 1 MB add no lines), and `.superlite/metrics.jsonl` has no `superlite:final-reviewer` stop newer than the merge-base commit. The reason asks for a final review on a packet or a stated reason. Off with `SUPERLITE_FINAL_REVIEW=off`; silent when `stop_hook_active`. Not in `hooks-cursor.json`. `capture-agent-stop` records final-reviewer stops even without a run.

## Detecting an active run

For a third-party hook, use the first of these that applies (the order of `hooks/superlite-state.sh` and `state.py`). 1. `SUPERLITE_STATE_DIR`, when set, is the `.superlite` folder. 2. Read `session_id` from the hook input and read the first line of `~/.superlite/sessions/<session_id>` (`$SUPERLITE_HOME/sessions/<session_id>` when `SUPERLITE_HOME` is set) as the bound `.superlite` folder; it counts while the folder exists and its `session` file is empty or names this session (another name means taken over). 3. Legacy: `<project>/.superlite` (`CLAUDE_PROJECT_DIR`, else the input `cwd`), unless its `session` file names another live session whose binding points at that folder. No such file or folder means no bound run. A run is active while that folder holds `pool.json`, `prime.md` or `stable.json`. `sl orchestrator end` archives those markers.

Warning: checkpoint mode leaves the tree dirty during a run by design, so a Stop hook that polices uncommitted files should stay silent while a run is active.
