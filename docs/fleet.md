# Fleet mode

## What it is

With fleet mode on, a superlite run executes every role (implementers, fixers, package reviewers, the final reviewer, research, test layers) in real Claude Code sessions or shell panes that live in Herdr: one worker per pane (`W1`, `W2`, ...), each started under the subscription account with the most headroom. The coordinator keeps the same loop (dispatch, task message, report, `commit_task`, reviews, fixes); with fleet off nothing changes and every agent stays an in-process call. You can watch and steer every worker in Herdr: worker `W1` appears there as the agent `sl-<repo>-<worktree>-w1`, the slug of its full name `sl:<repo>-<worktree>-W1` (lowercase, `:` and other characters outside `[a-z0-9_-]` become `-`, cut to 32 characters with the id kept whole). `<repo>` is the repository's folder name; `<worktree>` is `main` in the main checkout and the worktree's folder name without a leading `<repo>-` in a git worktree. Herdr keeps agent names unique per server: a name a live agent already holds gets 4 hex digits of the run root's path before the id. A batch lead is `sl-<repo>-<its worktree>-lead`. The pane label carries the full name, `sl:<repo>-<worktree>-<task> Wn` while a task or brief runs (then `reported, waiting for coordinator` or `BLOCKED-UI` after it), and the workspace label is `sl:<repo>-<worktree>`. `sl fleet name [ID] --plan P` prints the full name, also for an in-process agent's Agent `description`.

Turn it on by asking the coordinator to "use fleet": it runs `sl fleet on` before the first dispatch. Without that every agent stays in-process and Herdr shows only the coordinator. With fleet on, an in-process `Agent` call for a superlite role is blocked. That block reads the `fleet.json` of the run the session works in: `$SUPERLITE_STATE_DIR` when set, else the session's state folder; from a linked worktree, a state folder outside it (a binding to the main checkout) gives way to the worktree's own `.superlite`, so a worktree without a `fleet.json` has fleet off (#495). `sl fleet on` records who turned it on (`owner_session` and `owner_pid` in `fleet.json`); a fleet another session turned on does not block unless that session is still bound to the folder or runs in the same Claude process (after `/clear`), and a `fleet.json` without `owner_session` blocks as before. The block message names `--plan PLAN`: the plan file, or the state folder it names for a build without a plan (inline). Implementer workers cover the tasks of a plan with a taskgraph; an inline build without a taskgraph starts no implementer worker.

Fleet covers the implementer tasks of one taskgraph plan in one checkout: several tickets go into one plan and one run, not one worktree each. Fleet asked for but `sl fleet` unknown (compare `sl version` with the session-start line) or `fleet spawn` exits 3: report BLOCKED with the exact error before any dispatch; never fall back to in-process agents. `sl feedback add` comes in addition, never instead.

## Roles

Start one with `"$SL" fleet spawn --role R [--tier T] --plan PLAN`, then give it a brief with `fleet send Wn --brief FILE`.

| Role | Agent | Model and effort | Prime |
|---|---|---|---|
| `implementer` (default) | `superlite:implementer[-haiku]` | the tier's model (`--tier sonnet` or `haiku`), effort from the agent file | primed with `.superlite/prime.md`, then sent tasks; reused |
| `fixer` | `superlite:fixer-{sonnet,sonnet-high,opus}` (`--tier 1\|2\|3`, or `sonnet\|sonnet-high\|opus`) | sonnet medium, sonnet high, opus high | none; one brief, a fresh worker per fix |
| `package-reviewer` | `superlite:package-reviewer` | sonnet, medium | none; one brief |
| `final-reviewer` | `superlite:final-reviewer` | opus, high; a fresh worker per round | none; `.superlite/review-packet.md` |
| `research` | `superlite:researcher` (`agents/researcher.md`) | sonnet, low (`--tier haiku\|opus` pins another model; with fleet off the in-process researcher keeps the agent file's haiku); read-only (Read, Grep, Glob; no Write, Edit or shell) | none; one brief |

The reviewers take no `--tier`; an unknown role or tier exits 2 with `error: ...`. A test layer is not an agent: `fleet run --layer headless|tui|evals` runs `scripts/test_layers.py` in a shell pane and records the role `layer`.

Research worker limits: the researcher has only Read, Grep and Glob (spawn also disallows Edit, Write, NotebookEdit and Bash), so it cannot write a report file or run `git`, and it answers in at most 300 words with `file:line` references. `fleet wait` saves that reply as `<sd>/fleet/reports/<label>.md` (the `.json` next to it; the label is the brief's file name without `.md`): that file is the report. A brief that asks for a report file, or for more than 300 words, cannot be fulfilled: split it into one brief per question and one worker each. Research path: write the prompt to `<sd>/briefs/<name>.md`; `sl fleet spawn --role research --plan PLAN` prints `Wn`; `sl fleet send Wn --brief <sd>/briefs/<name>.md --plan PLAN`; `sl fleet wait Wn --plan PLAN` (Bash timeout 600000). PLAN is the plan file, or the state folder `.superlite` before a plan exists (a lead in brainstorming); without `--plan` the run is the current directory's (`SUPERLITE_STATE_DIR` in a lead pane, else the worktree's or the current folder's `.superlite`). `sl fleet report Wn` prints the saved report again. The researcher cannot reach documentation tools (context7, Xcode DocumentationSearch or any other MCP server) or the web (WebFetch, WebSearch): an API or library lookup stays with the coordinator, which does it itself and puts the answer into the brief.

- Every worker gets `--effort` from its agent file (frontmatter effort is ignored in a main-thread session), `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=0` and `SUPERLITE_FLEET_ROLE=<role>`.
- Briefs live in `.superlite/briefs/` (inside the worker's cwd; spawn adds `--add-dir` when the state dir is outside it). A brief is a file the worker reads, never pasted text.
- A one-turn worker (everything except the implementer) ends with a status line and one JSON block; `fleet wait` stops it once its status is final.
- Fleet relies on accounts in auto mode. A non-auto account stops reads outside the cwd at a permission dialog, which `wait` reports as `BLOCKED-UI`.

## Capacity

- A tab holds 4 panes and a pane never splits below 20 rows. The fifth worker, or a split that would leave a pane under 20 rows, opens a new tab in the same workspace; the next workers split that tab again.
- Accounts spread over every superlite session on the machine: each spawn records the worker's account in `~/.superlite/fleet/agents/<agent name>`, and the next spawn counts the live workers (`herdr agent list`) of other sessions too, a lead and its workers included, before it picks the account. Without an agent list it counts this run only.
- `current` and config dir entries that `claude-profile` knows are checked against that account's usage and caps like a named account; at its cap they are refused (`BLOCKED: no account with headroom`) and the others get the worker.
- A prime that stalls (`agent_prompt_stalled`) is resent once; a second stall is `BLOCKED`. `BLOCKED: Wn no READY` names the pane size (rows and columns), since a pane too small to show the reply is the usual cause.
- `sl accounts [--tier MODEL]` shows the headroom spawn sees: one line per account of `claude-profile usage --json`, `claude1 ok 5h=12% weekly=40%` or `claude2 skip 5-hour 95%` (the reason spawn skips it; `--tier` adds that model's scoped weekly cap). Without usage data it prints `accounts: no usage data from claude-profile usage --json` and `usage: sl accounts [--tier MODEL]` on stderr and exits 3.

## Prerequisites

- A running Herdr server and `herdr` on PATH (or `SUPERLITE_HERDR_BIN`).
- Each account's `CLAUDE_CONFIG_DIR` logged in once (run `claude` in it). The default account (`~/.claude`) is started with the variable unset: set to that path, Claude Code starts its first-run setup.
- Account names need `claude-profile` (it maps a name to its config dir and ranks accounts by usage). Config dir paths (an entry with a slash or starting with `~`, e.g. `--accounts ~/.claude-account1`; the account name is its basename) work without it, and `current` always works. Without `claude-profile`, a bare name fails at spawn with `BLOCKED: no config dir for account <name> (claude-profile list unavailable; pass a config dir path instead)` and `fleet on` prints a warning; the first allowed account is used. Without any account list, the single account `current` (the coordinator's own config dir) is used.

## Commands

Run as `"$SL" fleet ...`; `fleet --help` lists every subcommand (on, off, status, spawn, stop, report, send, keys, wait, run). All take `--plan PLAN` to find the run (the plan file or the run's `.superlite` folder); without it the run is the current directory's. A `--plan` that names no usable run exits 2 before anything runs: `error: --plan P: not a plan file or folder; pass the plan file or the run's .superlite folder, or leave --plan out to use the current directory's run` (`/dev/null`), or `error: --plan P: cannot create <dir>; ...` when its state folder cannot be created.

- `fleet on [--accounts claude1,claude3]` turns fleet mode on (default order: the `--accounts` flag, then `SUPERLITE_FLEET_ACCOUNTS`, then every account `claude-profile list --json` returns, then `current`).
- `fleet spawn --tier sonnet` (role `implementer`) starts a worker and primes it; prints `W1 account=claude1 pane=w6:p1 agent=superlite:implementer`. Exit 3 with `BLOCKED: ...` when no account has headroom or startup fails. A start that fails with `not an available shell` (a pane freed a moment ago) is retried once on the same pane after 3 s; a BLOCKED reason after that retry ends `; retried once`, and `--for-dispatch` adds `; rerun sl fleet spawn --for-dispatch` to its `BLOCKED: Tn not sent (...)` line. `--for-dispatch` also ends with one `review: Tn (<why>); run ... fleet spawn --for-review Tn --plan P` line per committed task that matches a review reason and has no review yet.
- `fleet send W1 T3 --plan PLAN` sends a task (`W1 T3 T4` for a batch); prints `W1 T3 sent`, or `W1 T3,T4 sent` for a batch. `fleet send W1 --text "use the v2 API"` sends free text, for example an answer to NEEDS_CONTEXT. A send (also `--brief` and `--text`) is resent once after a stall (`agent_prompt_stalled`) or a slow Herdr reply, unless the worker already shows `working`. Two of task ids, `--text` and `--brief` in one call (an empty `--text` counts) exit 2 with `error: send takes task ids, --text or --brief, not two of them` on stderr, before anything is sent. While a worker is busy in fleet.json (for example answering a `--text`), `dispatch`, `commit_task --dispatch` and `fleet spawn --for-dispatch` offer it no task; the round after `fleet wait` has reported it offers it again (#553).
- `fleet spawn --role fixer|package-reviewer|final-reviewer|research [--tier T]` starts a worker of that role (no prime); prints the same line plus ` role=<role>`.
- `fleet spawn --for-review Tn [Tm ...] --plan PLAN` (or `--package X`, the package's committed tasks) writes the review brief, starts a package-reviewer and sends it; task ids or `--package`, not both. When the review's root is another superlite checkout (a worktree of superlite itself) and its tasks own files under `skills/subagent-driven-development/scripts/` or `probes/`, the brief adds a `Worktree sl` line: that checkout's sl, for live checks of the tools those tasks add or change; every other command stays on the sl that holds the run's state (#513). `--plan` may be the run folder. A one-turn worker and a lead start lean: `--strict-mcp-config`, `--no-chrome` and `--disable-slash-commands`.
- A start that stays slow (no `working` or `blocked` within 30 s after the stall) is retried once on another account, with `Wn account A <why>; retrying on account B` on stderr; the same holds for a lead.
- `fleet send W1 --brief FILE [--label L]` sends a brief file; prints `W1 <label> sent`. The label defaults to the file's name without `.md`. `--full` (with `--brief`, final-reviewer workers only; exit 2 otherwise) asks for a full review, not the fast path.
- `fleet run --layer headless|tui|evals --plan PLAN` runs a test layer in a shell pane (the repo's `scripts/test_layers.py run <layer>`); prints `W5 layer-headless started account=claude3 pane=w6:p2`.
- `"$SL" findings route --plan PLAN REPORT.json ...` turns report findings into fixer briefs; prints `fixer tier=<sonnet|sonnet-high|opus> brief=<path> files=<a,b> task=<Tn>` per brief, or `findings: none`.
- `fleet wait [--timeout 540000] [W1 ...]` waits for busy workers. Prints `Wn <label> <STATUS> findings=<n> <json path>` (`W1 T3 DONE findings=0 <sd>/fleet/reports/T3.json`; the report text is the `.md` next to it) with `<STATUS>` one of `DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT`, `BLOCKED`, `APPROVED`, `CHANGES_REQUESTED` or `UNKNOWN` (no parsable block); a line with reported concerns carries ` concerns=N` after `findings=n`; a line read from the screen ends with ` (screen)`. A worker whose turn ends without a status is asked once for its report (`W1 T3 ASKED (turn ended without a report; asked once)`); the next miss is `UNKNOWN`; leads are never asked. The labelled form `Files changed:`, `Tests:`, `Summary:` and `Concerns:` lines read as a report when the json block is missing. A layer prints `Wn layer-headless GREEN|RED exit=<n> <log path>` plus its last line. `W1 T3 BLOCKED-UI <screen path>` plus the screen's last lines, and `TIMEOUT W1 W2` (space-separated) for the rest, stay as they were. A stop record whose transcript reads empty, or lacks the status its cut `last` line holds, is re-read for 10 s; after that the worker ends `UNKNOWN` with ` (transcript unread)` at the end of its line, is kept (not stopped), and its `.md` shows the cut line as a labelled block plus the last pane lines.
- A saved report JSON (`<sd>/fleet/reports/<id>.json`) carries a `red` string, the red-run evidence: the json block's non-empty `red`, else the reply's last `Red run:` line (a bullet, a bold or backticked label and CRLF line ends work), else `""`; a non-string `red` makes the block unparsable. The report contract `fleet send` appends asks for it between `tests` and `findings`, except in the final reviewer's.
- `fleet wait --any` returns as soon as one worker finishes and prints `BUSY W2 W3` for the workers still running; run it as a background command so the harness wakes the coordinator. A worker's Herdr pane label reads `Wn <label>` after a send, `Wn <label> reported, waiting for coordinator` once its report is collected and `Wn <label> BLOCKED-UI` on a blocked screen.
- `fleet report Wn [Wm ...]` prints the report `fleet wait` saved for each worker's last collected label (`<sd>/fleet/reports/<id>.md`, a layer's `.json`); a report label (`T3`, `FR1`) works too. Several ids print a `== <id> <path>` line before each report. A busy or blocked worker (`error: Wn is busy on T3; run sl fleet wait Wn first`), a worker with no collected report or an unknown id prints an `error:` line on stderr and exits 1; the others still print. It only reads.
- `fleet spawn --for-dispatch` sends every ready task and stops each evicted idle worker (`stopped W2` on stdout) and each ready implementer an earlier dispatch dropped from `pool.json`. It exits 3 with `BLOCKED: no ...prime.md; run build_prime --plan PLAN first` when the prime file is missing.
- `fleet keys W1 Down Enter` sends keys to a worker's pane, for a dialog.
- `fleet status` prints `fleet: on` and one line per worker, with the columns `context_k=` and `baseline_k=` on implementer lines only (the workers in `pool.json`). Eviction subtracts `baseline_k` (the READY reply's context) from `context_k`.
- `fleet stop W1` or `fleet stop --all` closes workers (`--all` also closes the workspace).
- `fleet off` stops all workers and turns fleet mode off. It writes its state first and closes the workspace last, so it is safe to run from inside the fleet's own workspace.

## How a run looks

dispatch prints `fresh tier=T agent=TYPE` or `agent=Wn` (never `poll`) -> `fleet spawn` (fresh only) -> `fleet send` -> `fleet wait` -> `commit_task`. A review or fix round: `fleet spawn --role package-reviewer|final-reviewer` -> `fleet send Wn --brief` -> `fleet wait` (`APPROVED` or `CHANGES_REQUESTED findings=n`) -> `findings route` -> one fresh fixer worker per printed line. State lives in `.superlite/fleet.json`; screens in `.superlite/fleet/screens/`. None of it is committed. A task that waits on a human step is held with `sl hold Tn --reason R` (ledger line `- Hold Tn: R`) and released with `sl hold --release Tn`; `dispatch` never offers it and prints `held=Tn R` on stderr, and `/superlite:status` lists each held task with its id and reason.

## Batch leads (backlog mode)

`/superlite:backlog` works a whole issue backlog from the main session. Main loop: `sl backlog plan` (a read-only triage worker proposes file-disjoint batches), `decide` (Max's answers and one ship approval), `start` (per batch a worktree and a lead worker, at most `--cap` at once; `start --note FILE` stores a standing note of at most 2000 characters that every later lead brief carries, an empty file clears it, and a running lead that started before it gets a `note: B lead L started before this note; sl backlog tell B --text ... tells it` line), `wait` (one line per lead that ends; a shipped batch's line ends `followups=N undone=M` for the follow-up and left-undone lines of the lead's notes), `answer` (resumes a lead that escalated), `tell B --text T` (messages a running lead). `plan --issues N --add` plans an urgent issue next to open batches and keeps running ones and the ship approval; an `overlap: B shares <files> with B2 (<state>): ...` line names files a new batch shares with an open one, and each lead brief lists `Files other open batches own`. `decide --approve-ship --source prompt` records a ship approval the user's prompt gave, and `decide --file` records who answered (`"by"`: `user`, `main` or a map per question; `answer --file` takes the same key). `skip` also takes an issue out of a parked batch and stops that batch's lead once it is empty. State lives in `<main root>/.superlite/backlog.json`; each shipped batch leaves a short summary in `.superlite/backlog/<B>.md`. Main starts in a fresh session: one that already loaded another superlite skill or command runs `/clear` first. `backlog plan` cuts an over-long question header (12), option label (60) and description (200) and names each cut in a `shortened:` line (at most 5, then `shortened: K more`). `start B7 B10` checks each id on its own: refusals print first, the others still start, exit 2 when any was refused. A batch whose lead's merge was denied is shipped by main with `sl backlog ship B merge --from-main` (main only): it takes the ship lock, rebases (a conflict aborts the rebase), bumps the version again when the default branch already has it, runs `maxapp ship`, marks the batch shipped, writes its summary, releases the ship lock and stops its lead; a batch main shipped by hand (`maxapp ship -C <worktree>`) is recorded with `sl backlog ship B done --pr N [--version X]`.

An option label over 60 characters is cut at its last whole word, and its full text (without ` (Recommended)`) leads its description, which is then cut to 200. A `plan` refused by planned or parked batches ends `; sl backlog plan --reset drops them and plans every open issue again (shipped batches stay)`; with a running or needs_decision batch it ends `; --reset is refused too while a batch is running or needs_decision` instead (exit 2). `sl backlog status` with no batch open ends with the line `next: sl backlog plan`.

A lead is a fleet worker of main's run with role `lead`, started in its batch worktree with its own `.superlite` and its own fleet, with `--autocompact` set to main's window. Env: `SUPERLITE_FLEET_ROLE=lead`, `SUPERLITE_FLEET_AGENT=lead`, `SUPERLITE_FLEET_WORKER=Wn`, `SUPERLITE_STATE_DIR=<worktree>/.superlite`, `SUPERLITE_FLEET_PARENT_DIR=<main .superlite>`. It runs with `--permission-mode auto` and may only run `Bash(maxapp ship *)` and `sl backlog ship *`; `AskUserQuestion` is disallowed. Hooks treat it as a coordinator, and fleet panes answer permission dialogs with no.

Taking a run over: a session that continues another session's run (a resumed lead, or a coordinator whose session ran out of usage) runs `sl orchestrator takeover --plan .superlite` first (a plan path works too). `sl orchestrator end`, `set`, `approve` and `bind` refuse a run folder another live session owns and name that command, and `sl finish` prints it as a hint; `takeover` binds the run to this session and prints `orchestrator: run <dir> taken over from session <id>; this session owns it now`.

Ship lock: leads ship one at a time. `sl backlog ship B lock` takes the machine-wide ship lock `~/.superlite/locks/ship-<repo>.lock` (`{batch, lead, agent, repo, time}`); `merge` or `release` frees it. A lock is stale when its lead's agent is no longer live; the next `lock` takes it over. After `merge` the lead's PR is merged and `sl backlog ship` fast-forwards the main checkout, so the next lead builds on it.

Main's bulk close of incidents uses `sl incident resolve --kind K --reason R`, which closes every open incident of that kind.

Escalation: a lead that needs a major decision lets its workers finish, writes `.superlite/question.json` (`{"questions": [...]}`, the AskUserQuestion shape) and ends with `Status: NEEDS_DECISION`. `backlog wait` prints the batch, main asks Max and runs `backlog answer B --file F`, which writes `answer-<n>.json` and resumes the lead. A lead's `question.json` is cut like `plan`'s (header 12, option label 60 at its last whole word, option description 200; each cut named in a `B shortened:` line after the `needs_decision` line), never its question text; a file still invalid after the cut is sent back to the lead once, and the next invalid one parks the batch with `invalid question.json: <errors>`. A lead that stops without a Status line gets one re-prompt; its next such stop parks the batch with `no status in stop text: <text>` (`start` and `answer` reset it). A stop record whose transcript lags is re-read for 10 s from the stop; then a cut `last` line holding a status parks the batch with `<cut line> (transcript unread)`.

| Step | Do | Expect |
|---|---|---|
| Lead ships a batch | `backlog plan`, `decide`, `start B1`, `wait` | a lead builds in its worktree; `wait` prints the batch as shipped after `lock`, `bump`, `merge` |
| Escalation | A lead writes `question.json` and ends `NEEDS_DECISION` | `wait` names the batch as needs_decision; `answer B1 --file F` resumes it |
| Two leads ship in turn | Start two batches; both reach `ship lock` | the second `lock` waits until the first `merge` or `release` |
| Lead stops without a status | A lead ends its turn with no Status line, twice | the first stop prints nothing and re-prompts the lead; the second parks the batch with `no status in stop text: <text>` |
| Main ships a denied merge | The lead's `merge` was denied and `wait` parked the batch; main runs `ship B merge --from-main` | `status` shows the batch shipped with its PR; the ship lock is free |

## Troubleshooting

- Trust dialog (`Yes, I trust this folder`): accepted automatically at spawn, also when it comes up after a one-turn worker or a lead has started. A primed worker whose pane shows it gets Down, Enter and the prime once more; a dialog that stays open is named in the `BLOCKED` line.
- `Select login method` or another startup block: the account's login expired. Run `claude` once in that account's config dir. The screen is in `.superlite/fleet/screens/Wn.txt`.
- `BLOCKED: Wn no READY (pane R rows, C cols)`: the prime prompt did not land. Check with `herdr agent read sl-<repo>-<worktree>-wn`.
- `agent_prompt_stalled` (a herdr error code, shown in the `error:` line): spawn resends the prime once; a second stall is BLOCKED. For a `fleet send` to a worker that was mid-turn: run `fleet wait`, then resend.
- `Blocked: fleet is on` in a session that never ran `sl fleet on`: the folder the message names holds a fleet without `owner_session` (turned on before #495). When its run is finished, `sl fleet off --plan <that folder>`; to use it, `sl fleet on --plan <that folder>` takes it over.

## Run root and task trees

- Every worker edits the shared run root: the checkout the run lives in (a lead's batch worktree), not a copy. `commit_task` commits from there.
- On a compiled stack (Swift, Go, Rust, C#, or another non-Python stack with `"isolate": true` in `.superlite/test-cmd.json`; a pytest run ignores it) `run_tests --task Tn` builds and tests in its own tree, `.superlite/trees/Tn`: the base commit plus the working-tree changes minus the files of unfinished sibling tasks (`--fast`), or plus Tn's own files only (`--full`). A task's test run there does not see another running task's files, and a file the task does not own is missing from its `--full` tree. Other stacks (pytest) test in the run root.
- A fleet worker's `run_tests --fast` without `--task` (a package reviewer, a fixer) on such a stack builds and tests in the worker's own tree, `.superlite/trees/worker-Wn`: the base commit plus the working-tree changes minus the files of unfinished tasks and the changed files another busy fixer's or reviewer's brief names (unless the worker's own brief names them too). Its build folder (SwiftPM `.build`, Xcode DerivedData) is its own, so a reviewer does not compile a running sibling's red tests and fixers may run at once. A lead's runs, `--full` runs and fleet-off (Agent) workers test in the run root: there, send one fixer at a time per run root on a compiled stack, the next after the previous fixer's `commit_task`. On other stacks fixers with disjoint files may run at once; a test that turns red in another fixer's file is rerun after that fixer's commit.

## Limits
