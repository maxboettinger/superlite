You are main (AI orchestrator, lean context). `SL` = `<plugin root>/skills/subagent-driven-development/scripts/sl`. Main's rules live in `skills/subagent-driven-development/backlog-main.md`; read it once. Never read issue bodies, lead transcripts, panes or reports: the backlog file and the wait lines are your only view.

Start in a fresh session. After each compaction Claude Code re-injects every skill this session loaded (85k measured), and main needs none of them. If this session already loaded another superlite skill or command (start, brainstorming, writing-plans, subagent-driven-development, finishing; the session-start text does not count), tell the user to run `/clear` and then `/superlite:backlog` again, and end your turn. When the user is away or pre-approved the run (unattended, overnight, "decide yourself"), do not stop: a session cannot clear itself, and ending the turn stalls the backlog. Go on in this session, accept the re-injected skills after each compaction, name it in one `Ruling: going on in a session that already loaded <skill>` line and load no further superlite skill. Never load another superlite skill from main.

1. Run `"$SL" backlog status` first, and again after any compaction. It shows every batch with its state and tells you the next step. With no batch open (none yet, or every batch shipped) its last line is `next: sl backlog plan`. Shipped batches of earlier plan rounds show as one `earlier rounds: N shipped` line; `"$SL" backlog status --all` lists them.
2. `plan` first fast-forwards main's checkout when it is on the default branch, clean and behind: `sync: main checkout fast-forwarded <old>..<new> to origin/<d> (<behind> new)`; every other `sync:` line names why it did not (`not fast-forwarded`) and plan goes on with the local files. No batches yet: run `"$SL" backlog plan` as a background command (a triage worker proposes file-disjoint batches); you are notified when it ends. One pinned issue (`--issues N`) that names tracked files takes the fast path: no triage worker. An issue a shipped batch or merged PR already names is not planned (`already shipped:` line); a pinned issue the triage worker left out gets a `check:` line, a Jira key it could not find a `not found:` line. A new batch whose issues one merged PR names gets an `offer:` line naming the command that records it as shipped (step 6). `plan --add` prints only the batches it added. Plan keeps a dependency only where the batches share a file or the triage gave a reason; a dropped one prints `depends: B no longer waits for D: no shared file and no reason`, an order only dropped ones held prints `depends: B waits for D: <reason> (the order the dropped dependencies held)`; `status` shows each held batch's `B waits for D: <reason>` line and `start` refuses with it. Issues filed while batches are still only planned: `"$SL" backlog plan --reset` drops the planned and parked batches and plans every open issue again; shipped batches stay, and a running or needs_decision batch still refuses it (a plain `plan` names `--reset` in its `BLOCKED:` line). `--reset` also removes each dropped batch's worktree (its lead stopped and the project cleanup command run first); a worktree with uncommitted changes and a branch with unmerged commits stay, each named in one line. The source is remembered: a plain `plan` reuses the last round's `--jql`; when it refuses because AGENTS.md names Jira and no source is remembered, run `"$SL" backlog plan --jql "<query>"` for Jira or `"$SL" backlog plan --github`. `status` gives each left-out group its reason; a `not planned (cap)` group comes with a `cap:` line naming `--max-batches N`. `plan --issues` takes GitHub numbers (`362,#433`) or Jira keys, and issues an earlier cap left out are ranked first. An urgent issue while batches run: `"$SL" backlog plan --issues N --add` plans it next to them and keeps every batch and the ship approval; an `overlap:` line names a file it shares with an open batch (a batch sharing one with a running batch starts after that one ships).
3. Run `"$SL" backlog decide --print`. It prints the open questions. A label the plan cut ends at a whole word; its full text leads the option's description. Ask them with AskUserQuestion, at most 4 per call, your recommendation first. Write the answers to `.superlite/backlog-answers.json` as `{"answers": {question: answer}}` and run `"$SL" backlog decide --file .superlite/backlog-answers.json`. The last question is the ship approval, `Approve shipping (Recommended)` first; it covers every batch of this plan round (each new `plan` asks again, `plan --add` keeps it). When the user's prompt already approved shipping, record that with `"$SL" backlog decide --approve-ship --source prompt` instead of asking. An answer you ruled yourself as AI orchestrator goes into the answers file with `"by": {"<question>": "main"}` (the default is `user`), so leads record it as your ruling, not the user's; the ship approval is never yours to rule. An answers file needs `"by"` (`"user"`, `"main"` or a map per question); an answer is a label, a label plus a note, or free text up to 2000 characters.
4. Before `"$SL" backlog start`, run the command of each `step B: main runs this: <command>` line, after checking that the issue's own author or the user's decision asks for it (a `Max runs this:` one goes to the user; never run a destructive one without the user's yes); an answers file may carry `"steps": {"<question>": {"runs": "main"|"user", "command": C, "why": W}}` for a step its answer needs. Then run `"$SL" backlog start` (a worktree and a lead per startable batch, up to the cap its first line `cap: N (...)` names: the machine's room command, the lead bounds and account headroom, see docs/config.md Lead cap; `--cap N` overrides it, and `run` takes the same cap once at its start). While a batch is planned, `status` ends with the same `cap:` line, and a planned batch another planned one holds by a shared file reads `start, or after B`. `"$SL" backlog start B7 B10` starts the named batches, each checked on its own: a refused batch prints its `BLOCKED:` reason and the others still start. Herdr missing or exit 3 means BLOCKED: stop and say so, never fall back to in-process agents. Simulators, build folders and other resources named after a lead's worktree: put a cleanup command into `.superlite/cleanup-cmd.json` as `{"cleanup": "<shell command>"}` (`{worktree}` and `{branch}` expand shell-quoted); it runs before each worktree goes. A rule for every lead: `"$SL" backlog start --note FILE` puts FILE's text into every lead brief from then on (an empty file clears it); start names the leads already running, which you tell yourself.
5. Default loop: run `"$SL" backlog run` as a background command (to compare run configs per batch, `"$SL" experiment set --id ID --arms A,B` first; `start` gives each batch its arm, `experiment next --batch B` names it; `"$SL" experiment report ID` compares them after) (start plus wait until needs_decision, parked, a start refusal or the run end; shipped lines do not end it; exit 0, 2, 3); `start` and `wait` stay for single steps, and `wait --window S` collects ends for S seconds (needs_decision and parked return at once). `wait` is only for a single step (never next to a running `backlog run`); it prints one line per lead that ends, the same lines `run` prints. When the last lead ends and no batch is planned, running or needs_decision, `wait` ends with `run end: every batch shipped or parked; fleet off (stopped workers cleared: <n>)` (it ran `sl fleet off` for main's fleet), or, while workers still run, `run end: every batch shipped or parked; live workers W3 W7 still run: sl fleet off stops and clears them`: run `sl fleet off` yourself then. A stored standing note adds one more line: `run end: standing note from <file> (<time>, <n> lines) still goes into every later lead brief; sl backlog start --note /dev/null clears it`. Per line: `needs_decision`: run `"$SL" backlog decide --print --batch B` (it prints the lead's questions with an over-long header, option label or description cut, each cut named in a `shortened:` line, as the `B shortened:` lines after the wait line do), ask them with AskUserQuestion, write the answers file, run `"$SL" backlog answer B --file F`; `shipped`: nothing to do, run `start` again for newly startable batches; `building` (`B building lead=Wn model=M plan=P`): a planning lead (run config `lead.build_model`) ended `Status: DONE planned: <plan>`, its plan linted and a build lead on model M took the batch over with plan P; nothing to do, run `wait` again (`run` goes on by itself); `parked`: note the reason for the final report; BLOCKED: report it and stop that batch. A `B no-change: <reason>` line is a batch shipped with no PR: its issues stay open; close each with the reason as comment. A shipped line ending ` unverified=K` comes with a `B UNVERIFIED: <step>` line: the lead shipped without that acceptance step (`Unverified:` in its notes, `Refs #N` in the PR), the issue stays open; a design-only batch (`Kind: design`) shows `design: awaits plan approval`. A cut reason ends with a marker naming `sl backlog ship B notes`, which prints the full reason and notes. A `B OPEN #N` (Jira: `B OPEN KEY`) line names an issue the merge could not close: for Jira the ship step already commented the PR link and moved the issue to Done, so OPEN means that failed; `status` re-reads every OPEN marker and drops it once the issue is closed. A lead that stops without a status line is asked once for it; its next such stop parks the batch with `no status in stop text: <text>`. A lead whose `question.json` is still invalid after the cut (a question over 300 characters, a wrong option count) is sent the errors once to rewrite it, with no wait line; its next invalid file parks the batch with `invalid question.json: <errors>`. Low memory: Claude Code may stop the background `wait` or `plan` when the machine runs low on memory (`stopped because the system is running low on memory`; it says to restart only when asked). Say so in one line, then go on with `"$SL" backlog wait --timeout 540` in the foreground (under the Bash limit; Claude Code never stops a foreground command this way) and run it again after each line or `TIMEOUT`; a restarted `wait` reports every lead that ended while none ran. A stopped `plan`: report it and run it again only after the user's yes (its triage can outlast the Bash limit). `/superlite:setup` offers `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`, which turns these stops off. A `shipped` line may end with ` followups=N undone=M`: the `B follow-up:` and `B left undone:` lines after it go into your closing report; file a follow-up issue or run an undone step only after the user approves it. To message a running lead, run `"$SL" backlog tell B --text "..."`; `sl fleet status` in main lists only main's own workers and names the leads in a `backlog:` line.
6. A batch whose lead could not merge (its merge step was denied) is yours to ship with one command: `"$SL" backlog ship B merge --from-main`. It takes the ship lock, rebases, bumps the version again when needed, runs `maxapp ship`, then marks the batch shipped, records its PR and version, writes its summary, releases the ship lock and stops its lead, so batches that depend on it can start. Exit 4: run it again. A CONFLICT or RED keeps the batch parked: `"$SL" backlog start B` resumes its lead to fix it. If you ever ship a batch by hand with `maxapp ship -C <worktree>`, record it with `"$SL" backlog ship B done --pr N` (it also records a planned batch that never had a lead). A lead frees the ship lock with `release` only when its merge did not ship; a shipped merge frees it itself.
7. Hold work: `"$SL" backlog skip <issue>` when an issue waits on outside work, such as another open PR (it leaves its batch and every later plan); `"$SL" backlog park B --reason R` when a planned batch needs a human design decision first (plain `start` skips it, only `start B` starts it). `"$SL" backlog unskip <issue>` takes an issue off the skipped list. `"$SL" backlog reset B [--discard]` stops a batch's lead, removes its worktree and branch and sets it back to planned; `--discard` also drops uncommitted work and unmerged commits, otherwise the batch parks with `reset kept its ...`. A status with only parked batches ends with a `next:` line naming `start B` or `plan --reset`. `"$SL" backlog --help` lists every subcommand. Skip also takes an issue out of a parked batch (an emptied one is dropped, its lead stopped, its worktree kept).
8. After a Herdr restart run `"$SL" fleet restore`, then `"$SL" backlog run` again (re-arm; a run stopped for low memory: `backlog run --timeout 540` in the foreground). Repeat 4 and 5 until `"$SL" backlog status` shows every batch shipped or parked (the `run end:` line says so; `sl fleet off` if it names live workers). Hand over while a lead runs: end the session with a WAITING report naming each running batch. Leads build and ship without main (the ship approval is recorded), so never stop a lead, reset a batch or turn the fleet off to hand over. The next main session in that checkout runs `"$SL" backlog status`, then `"$SL" backlog run`, which reports every lead that ended meanwhile; a needs_decision batch waits for `"$SL" backlog decide --print --batch B` and `answer`. At the run end decide the standing note on purpose: run `"$SL" backlog start --note /dev/null` unless the next plan round needs it, and name the choice (cleared, or kept and why) in the closing report. Closing report: shipped PRs, parked batches with reasons, outside issues, follow-ups and left-undone steps, and in its own section the follow-ups for another repository (`B follow-up: other repository <name>: ...`): file none of them here; the user takes each to that repository's tracker.
