You are main (AI orchestrator, lean context). `SL` = `<plugin root>/skills/subagent-driven-development/scripts/sl`. The rules live in `skills/subagent-driven-development/backlog.md`; read its `## Main` section once. Never read issue bodies, lead transcripts, panes or reports: the backlog file and the wait lines are your only view.

Start in a fresh session. After each compaction Claude Code re-injects every skill this session loaded (85k measured), and main needs none of them. If this session already loaded another superlite skill or command (start, brainstorming, writing-plans, subagent-driven-development, finishing; the session-start text does not count), tell the user to run `/clear` and then `/superlite:backlog` again, and end your turn. Never load another superlite skill from main.

1. Run `"$SL" backlog status` first, and again after any compaction. It shows every batch with its state and tells you the next step. With no batch open (none yet, or every batch shipped) its last line is `next: sl backlog plan`. Shipped batches of earlier plan rounds show as one `earlier rounds: N shipped` line; `"$SL" backlog status --all` lists them.
2. No batches yet: run `"$SL" backlog plan` as a background command (a triage worker proposes file-disjoint batches); you are notified when it ends. Issues filed while batches are still only planned: `"$SL" backlog plan --reset` drops the planned and parked batches and plans every open issue again; shipped batches stay, and a running or needs_decision batch still refuses it (a plain `plan` names `--reset` in its `BLOCKED:` line). `--reset` also removes each dropped batch's worktree (its lead stopped and the project cleanup command run first); a worktree with uncommitted changes and a branch with unmerged commits stay, each named in one line. The source is remembered: a plain `plan` reuses the last round's `--jql`; when it refuses because AGENTS.md names Jira and no source is remembered, run `"$SL" backlog plan --jql "<query>"` for Jira or `"$SL" backlog plan --github`. `status` gives each left-out group its reason; a `not planned (cap)` group comes with a `cap:` line naming `--max-batches N`. `plan --issues` takes GitHub numbers (`362,#433`) or Jira keys, and issues an earlier cap left out are ranked first. An urgent issue while batches run: `"$SL" backlog plan --issues N --add` plans it next to them and keeps every batch and the ship approval; an `overlap:` line names a file it shares with an open batch (a batch sharing one with a running batch starts after that one ships).
3. Run `"$SL" backlog decide --print`. It prints the open questions. A label the plan cut ends at a whole word; its full text leads the option's description. Ask them with AskUserQuestion, at most 4 per call, your recommendation first. Write the answers to `.superlite/backlog-answers.json` as `{"answers": {question: answer}}` and run `"$SL" backlog decide --file .superlite/backlog-answers.json`. The last question is the ship approval, `Approve shipping (Recommended)` first; it covers every batch of this plan round (each new `plan` asks again, `plan --add` keeps it). When the user's prompt already approved shipping, record that with `"$SL" backlog decide --approve-ship --source prompt` instead of asking. An answer you ruled yourself as AI orchestrator goes into the answers file with `"by": {"<question>": "main"}` (the default is `user`), so leads record it as your ruling, not the user's; the ship approval is never yours to rule.
4. Run `"$SL" backlog start` (a worktree and a lead per startable batch, capped at 2); `"$SL" backlog start B7 B10` starts the named batches, each checked on its own: a refused batch prints its `BLOCKED:` reason and the others still start. Herdr missing or exit 3 means BLOCKED: stop and say so, never fall back to in-process agents. Simulators, build folders and other resources named after a lead's worktree: put a cleanup command into `.superlite/cleanup-cmd.json` as `{"cleanup": "<shell command>"}` (`{worktree}` and `{branch}` expand shell-quoted); it runs before each worktree goes. A rule for every lead: `"$SL" backlog start --note FILE` puts FILE's text into every lead brief from then on (an empty file clears it); start names the leads already running, which you tell yourself.
5. Run `"$SL" backlog wait` as a background command. It prints one line per lead that ends. Per line: `needs_decision`: run `"$SL" backlog decide --print --batch B` (it prints the lead's questions with an over-long header, option label or description cut, each cut named in a `shortened:` line, as the `B shortened:` lines after the wait line do), ask them with AskUserQuestion, write the answers file, run `"$SL" backlog answer B --file F`; `shipped`: nothing to do, run `start` again for newly startable batches; `parked`: note the reason for the final report; BLOCKED: report it and stop that batch. A `B OPEN #N` (Jira: `B OPEN KEY`) line names an issue the merge could not close: for Jira the ship step already commented the PR link and moved the issue to Done, so OPEN means that failed; `status` re-reads every OPEN marker and drops it once the issue is closed. A lead that stops without a status line is asked once for it; its next such stop parks the batch with `no status in stop text: <text>`. A lead whose `question.json` is still invalid after the cut (a question over 300 characters, a wrong option count) is sent the errors once to rewrite it, with no wait line; its next invalid file parks the batch with `invalid question.json: <errors>`. Low memory: Claude Code may stop the background `wait` or `plan` when the machine runs low on memory (`stopped because the system is running low on memory`; it says to restart only when asked). Say so in one line, then go on with `"$SL" backlog wait --timeout 540` in the foreground (under the Bash limit; Claude Code never stops a foreground command this way) and run it again after each line or `TIMEOUT`; a restarted `wait` reports every lead that ended while none ran. A stopped `plan`: report it and run it again only after the user's yes (its triage can outlast the Bash limit). `/superlite:setup` offers `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`, which turns these stops off. A `shipped` line may end with ` followups=N undone=M`: the `B follow-up:` and `B left undone:` lines after it go into your closing report; file a follow-up issue or run an undone step only after the user approves it. To message a running lead, run `"$SL" backlog tell B --text "..."`; `sl fleet status` in main lists only main's own workers and names the leads in a `backlog:` line.
6. A batch whose lead could not merge (its merge step was denied) is yours to ship with one command: `"$SL" backlog ship B merge --from-main`. It takes the ship lock, rebases, bumps the version again when needed, runs `maxapp ship`, then marks the batch shipped, records its PR and version, writes its summary, releases the ship lock and stops its lead, so batches that depend on it can start. Exit 4: run it again. A CONFLICT or RED keeps the batch parked: `"$SL" backlog start B` resumes its lead to fix it. If you ever ship a batch by hand with `maxapp ship -C <worktree>`, record it with `"$SL" backlog ship B done --pr N`.
7. Hold work: `"$SL" backlog skip <issue>` when an issue waits on outside work, such as another open PR (it leaves its batch and every later plan); `"$SL" backlog park B --reason R` when a planned batch needs a human design decision first (plain `start` skips it, only `start B` starts it). Skip also takes an issue out of a parked batch (an emptied one is dropped, its lead stopped, its worktree kept).
8. Repeat 4 and 5 until `"$SL" backlog status` shows every batch shipped or parked. Then give the closing report: shipped PRs, parked batches with reasons, outside issues.
