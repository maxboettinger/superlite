Check and report, changing nothing without a yes:
- the project language and test command (`sl testcmd`: report its `command` and `origin`, the file it came from: the project's `.superlite/test-cmd.json`, the main checkout's, the user-level `~/.config/superlite/test-cmd.json` entry for the project's language, or `detection`) and that it runs. When `origin` is not a `test-cmd.json` file, run `sl testcmd --propose`: `proposal` is the project's own test command (a project test script such as `Scripts/test.sh`, `scripts/test` or `bin/test`, else a Makefile `test` target, else the detected command; null for a Python project or when nothing is found), `from` where it came from, and `target` the file it would write (the root's own, also in a linked worktree; `sl testcmd --write --shared` writes the main checkout's, which every worktree without its own reads). The fix line proposes that command, or asks for one when `proposal` is null; on a yes `sl testcmd --write` writes it (`--test CMD` writes the command the user names instead; it never overwrites a `test-cmd.json`), so `sl run_tests` and every worker find it;
- for a project with an app, widget, app extension or web UI target: whether its `.superlite/test-cmd.json` (the main checkout's from a linked worktree) holds a `launch` entry, which says per platform whether a worker may launch the app and with which data. Work it out from the code: the platforms the targets build for; whether a worker's own simulator, macOS launch or browser can run it (not a Debug macOS app that shares its bundle id, container or Keychain with the user's installed app; an app paired with its server shows only what its demo data shows); and which launch arguments, fixture files, URLs or previews reach which states. The fix line proposes the entry, for example `"launch": {"ios": {"worker": true, "data": "-demo: signed-in demo account with 3 lists; no server pairing"}, "macos": {"worker": false, "why": "the Debug app shares bundle id, container and Keychain with the installed app", "data": "SwiftUI previews only"}}`; on a yes add it to that file and keep its other keys (a project without the file gets its test command first). `build_prime` copies it into every implementer's prime, and plans name its launch arguments and fixtures in their `## Running-app checks` `reach:` parts;
- Python 3.10+ for the `sl` tools;
- the model tiers in `config/models.json` and `config/routing.json`;
- whether superpowers is also enabled (two process skills compete: suggest disabling one for this project);
- whether `.superlite/` is gitignored;
- in Claude Code's interactive CLI only (`CLAUDE_CODE_ENTRYPOINT=cli`): whether `CLAUDE_CODE_FORK_SUBAGENT` is `0`. Otherwise Claude Code asks every background agent's model for a 3-5 word status line every 30 s, sending the agent's transcript, or a few hundred characters of notes when the server serves the short mode; superlite never reads it and the requests appear in no transcript, so the budget cannot count them (`agent_summary`; anthropics/claude-code#86879). The fix line offers to add `"CLAUDE_CODE_FORK_SUBAGENT": "0"` to the `env` map of the user settings (`$CLAUDE_CONFIG_DIR/settings.json`, default `~/.claude/settings.json`; keep the other keys). It takes effect in the next session and removes only the `fork` subagent type, which superlite never uses.
- in Claude Code only: whether the user settings (`$CLAUDE_CONFIG_DIR/settings.json`, default `~/.claude/settings.json`) let fixer agents commit: `permissions.allow` holds `Bash(*/skills/subagent-driven-development/scripts/sl commit_task *)`. Without it, auto mode's classifier denies the fixers' `sl commit_task` calls and the coordinator commits for them. Allow rules are checked before the classifier, for subagents too, and a plugin cannot ship one. The fix line offers to add that rule to `permissions.allow` (keep the other entries and keys).
- in Claude Code only: whether an auto-compact window is set, so a long orchestrator session compacts and continues by itself: `autoCompactWindow`, or a `modelSettings.<model>.autoCompactWindow` that `/autocompact` saved, of 500000 or less in the user settings (`$CLAUDE_CONFIG_DIR/settings.json`, default `~/.claude/settings.json`), or `CLAUDE_CODE_AUTO_COMPACT_WINDOW` in the environment. Without one, a model with a 1M window compacts only near its limit (about 967k tokens): every turn pays for the whole context and the user has to run `/compact` by hand. With one, Claude Code compacts at the window, `hooks/pre-compact` tells the summary what to keep, and `hooks/session-start` tells the session to go on and shows it the run state. A plugin cannot ship the setting. The fix line offers to add `"autoCompactWindow": 400000` to the user settings (keep the other keys); it applies to every Claude Code session of that account, at the latest from the next session. `/autocompact 400k` sets the same for the current model only.
- in Claude Code only, for fleet and backlog runs: whether `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP` is `1`, in the environment or in the `env` map of the user settings (`$CLAUDE_CONFIG_DIR/settings.json`, default `~/.claude/settings.json`). Without it, when the machine runs low on memory Claude Code stops an idle session's background commands (`sl fleet wait`, `sl backlog wait`, `sl backlog plan`) and tells the agent to restart them only when asked, so an unattended coordinator hears no worker or lead end and the run stalls. Setting it from a shell command has no effect. The fix line offers to add `"CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP": "1"` to the `env` map of the user settings (keep the other keys); it takes effect in the next session. Leads wait in the foreground, which Claude Code never stops this way.
Give a pass or fix line for each.
